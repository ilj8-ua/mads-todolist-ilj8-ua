Preguntas Trampa del Profesor (Defensa Oral)
❓ 1. ¿Por qué en los tests de repositorio pusisteis @Transactional pero en los de servicio NO?
Respuesta técnica: En los tests de repositorio (EquipoTest) se pone @Transactional para que Hibernate mantenga abierta la sesión durante las comprobaciones y haga rollback automático al terminar cada test, dejando la BD limpia. En cambio, en EquipoServiceTest no se debe poner porque el test debe simular exactamente el entorno del controlador web en producción (sin una transacción abierta por defecto). Si pusiéramos @Transactional en el test de servicio, ocultaríamos errores gravísimos como que a un método del servicio se le hubiera olvidado poner @Transactional o que se intente acceder a datos perezosos (Lazy) fuera de la sesión.
❓ 2. ¿Cómo evitasteis que al eliminar un equipo se borrasen los usuarios pertenecientes?
Respuesta técnica: En primer lugar, la relación @ManyToMany no tiene configurado CascadeType.REMOVE ni ALL. En segundo lugar, en el método eliminarEquipo() del servicio, antes de llamar a equipoRepository.delete(equipo), iteramos sobre los miembros y ejecutamos equipo.removeUsuario(usuario). Esto desvincula a los usuarios eliminando las filas de la tabla de unión equipo_usuario sin tocar la tabla usuarios.
❓ 3. ¿Por qué se usa `new HashSet<>(equipo.getUsuarios())` al desvincular en eliminarEquipo?
Respuesta técnica: Si iterásemos directamente sobre equipo.getUsuarios() y dentro del bucle llamásemos a equipo.removeUsuario(usuario), estaríamos eliminando elementos de la misma colección que el iterador de Java está recorriendo en ese instante. Java detecta esta incoherencia y lanza inmediatamente una excepción ConcurrentModificationException. Al envolverla en new HashSet<>(), creamos una copia defensiva para iterar sobre ella mientras modificamos la colección original sin peligro.
❓ 4. ¿Por qué tenéis dos workflows de GitHub Actions?
Respuesta técnica: • developer-tests.yml corre sobre H2 en memoria RAM: es súper rápido (30 seg) y da feedback inmediato al desarrollador en cada push.
• integration-tests.yml levanta un servicio Docker con PostgreSQL 13 real, espera con pg_isready y ejecuta los tests de integración: garantiza que no haya diferencias de sintaxis SQL, tipos de datos o secuencias de claves primarias entre H2 y PostgreSQL antes de fusionar el Pull Request a main.
❓ 5. Si un usuario que NO es administrador hace un POST con Postman a `/equipos/1/eliminar`, ¿qué ocurre?
Respuesta técnica: No nos fiamos solo de que el botón esté oculto en el HTML con Thymeleaf. En el backend, el método eliminarEquipo del controlador invoca comprobarAdmin(). Este método comprueba si hay sesión y si usuario.isAdmin() == true. Si no lo es, lanza UsuarioNoAutorizadoException, que devuelve un código de estado HTTP 401 Unauthorized y aborta la petición antes de llamar al servicio.
❓ 6. ¿Por qué usamos DTOs (EquipoData) en lugar de pasar la entidad a la vista?
Respuesta técnica: 1. Evitar LazyInitializationException: La entidad Equipo tiene colecciones perezosas (Lazy). Si la vista intenta acceder a los usuarios cuando la transacción del servicio ya ha terminado, salta una excepción fatal.
2. Seguridad: Evitamos exponer campos internos o contraseñas.
3. Desacoplamiento: Los cambios en las tablas de la base de datos no rompen los formularios HTML. Mapeamos de entidad a DTO con ModelMapper.
❓ 7. ¿Por qué pusisteis `readOnly = true` en métodos de consulta?
Respuesta técnica: En métodos como findAllOrdenadoPorNombre() o recuperarEquipo(), @Transactional(readOnly = true) le indica a Hibernate que solo se van a leer datos. Hibernate desactiva el mecanismo de comprobación de modificaciones en memoria (*dirty checking*), ahorrando CPU y RAM, y permite que la base de datos optimice los bloqueos de lectura.

Quiz de Autoevaluación Móvil (10 Preguntas)

Responde mentalmente y pulsa el botón para validar si dominas el concepto.

1. ¿Qué es el ciclo Red-Green-Refactor?
1. Red: Escribir un test pequeño que especifique el requisito y verlo fallar.
2. Green: Escribir únicamente el código mínimo que lo hace pasar.
3. Refactor: Mejorar el código sin romper el test.
4. Commit: Registrar el incremento en Git.
2. ¿Cuántas líneas de código de producción por test exige MADS?
Entre 15 y 25 líneas por commit de test-code. Muestra avance incremental (baby steps) en lugar de programar todo de golpe.
3. ¿Qué nombre tiene la tabla intermedia creada por @ManyToMany?
equipo_usuario, con las columnas fk_equipo y fk_usuario.
4. ¿Por qué al editar un equipo se permite guardar dejando el mismo nombre?
Porque si el usuario entra a editar y pulsa "Guardar" sin alterar el nombre, el validador de nombres duplicados no debe saltar contra el propio equipo que se está editando (Test 6 de la Historia 010).
5. ¿Qué comando de Docker se usó para arrancar la BD de desarrollo?
docker run -d -p 5432:5432 --name postgres-develop -e POSTGRES_USER=mads -e POSTGRES_PASSWORD=mads -e POSTGRES_DB=mads postgres:13
6. ¿Por qué se usa FetchType.LAZY en la relación de equipos y usuarios?
Para que al recuperar un equipo no se traigan de golpe a memoria todos sus usuarios y todas las tareas de esos usuarios, lo que causaría problemas graves de lentitud y consumo de memoria.
7. ¿Qué script SQL se ejecuta al principio de cada test para limpiar datos?
clean-db.sql, que contiene: DELETE FROM equipo_usuario; DELETE FROM tareas; DELETE FROM equipos; DELETE FROM usuarios; (en ese orden para respetar claves foráneas).
8. ¿Cómo sabe la vista detalleEquipo.html si debe mostrar "Unirse" o "Salir"?
El controlador llama a equipoService.usuarioEnEquipo(idEquipo, idUsuarioLogeado) y pasa la variable booleana esMiembro al modelo. Thymeleaf usa th:if="${!esMiembro}" y th:if="${esMiembro}".
9. ¿Qué patrón se usa en los controladores tras un POST exitoso?
El patrón Post-Redirect-Get (PRG), usando return "redirect:/equipos" y RedirectAttributes.addFlashAttribute() para evitar reenvíos al pulsar F5.
10. ¿Qué se comprobó en la fase 2 con respecto a los fallos en GitHub Actions?
Se alteró un test para que fallase deliberadamente, se subió el commit, y se comprobó que el Pull Request quedaba bloqueado con una cruz roja (`X`). Tras corregirlo y hacer push, se puso en verde (`✓`) permitiendo el merge.

GitHub Actions y Flujos de Trabajo (CI)
developer-tests.yml (H2 en memoria)

Ubicación: .github/workflows/developer-tests.yml

YAML - developer-tests.yml
name: Developer tests
on: push
jobs:
  launch-tests:
    runs-on: ubuntu-latest
    container: openjdk:8-jdk-alpine
    steps:
      - uses: actions/checkout@v2
      - name: Launch tests with Maven
        run: ./mvnw test

Puntos clave:

• on: push: Se activa ante cualquier commit o PR subido a GitHub.

• container: openjdk:8-jdk-alpine: Ejecuta dentro de una imagen oficial de Java 8 sobre Linux Alpine.

• run: ./mvnw test: Ejecuta los tests del desarrollador usando el perfil por defecto (H2 en memoria). Tarda ~30 segundos.

integration-tests.yml (PostgreSQL real con Docker)

Ubicación: .github/workflows/integration-tests.yml

YAML - integration-tests.yml
name: Integration tests
on: push
jobs:
  container-job:
    runs-on: ubuntu-latest
    container: openjdk:8-jdk-alpine

    services:
      postgres:
        image: postgres:13
        env:
          POSTGRES_USER: mads
          POSTGRES_PASSWORD: mads
          POSTGRES_DB: mads_test
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    steps:
      - uses: actions/checkout@v2
      - name: Launch tests with Maven
        run: ./mvnw test -D spring.profiles.active=postgres
        env:
          POSTGRES_HOST: postgres

Puntos clave:

• services: postgres:: Levanta un contenedor Docker en red con la imagen postgres:13.

• options: --health-cmd pg_isready: Healthcheck vital. Evita que Maven intente conectar antes de que PostgreSQL haya terminado de arrancar.

• env: POSTGRES_HOST: postgres: En la red interna de GitHub Actions, el contenedor de la BD se localiza por el nombre del servicio (postgres).

La Metodología TDD (Test-Driven Development)
[1. RED] --> Escribir test que falla antes de tocar código. [2. GREEN] --> Escribir el código mínimo indispensable para que pase. [3. REFACTOR] --> Mejorar estructura y limpieza manteniendo el test verde. [4. COMMIT] --> Registrar incremento modular (15-25 líneas por test).
Reglas de Oro Exigidas en MADS

1. Baby Steps: No se hacen commits grandes. Hay un commit por cada test superado.

2. Controllers limpios: Los controladores solo reciben peticiones HTTP, llaman al servicio y devuelven la vista. Nunca contienen validaciones ni lógica de negocio.

3. Transacciones: • En el servicio: @Transactional en métodos de escritura, y @Transactional(readOnly = true) en consultas.
• En tests de repositorio: Sí (hace rollback automático).
• En tests de servicio: NO (deben simular el comportamiento real del controller).

@Transactional
public void eliminarEquipo(Long idEquipo) {
    Equipo equipo = equipoRepository.findById(idEquipo).orElse(null);
    if (equipo == null) {
        throw new EquipoServiceException("Equipo no encontrado");
    }
    // Copia con new HashSet para evitar ConcurrentModificationException
    for (Usuario usuario : new HashSet<>(equipo.getUsuarios())) {
        equipo.removeUsuario(usuario);
    }
    equipoRepository.delete(equipo);
}
